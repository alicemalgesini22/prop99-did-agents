# Reflection

*Drafted with help from Claude (claude.ai) from my notes and `mistakes.md`, then read and checked by me. The full analysis is in `reports/run_comparison.md`; errors are numbered as in `mistakes.md`.*

**What I did.** I asked whether California's Proposition 99 reduced per-capita cigarette sales, using difference-in-differences. I built three agents in OpenCode (one that asks before every action, one that runs alone, one read-only reviewer) and ran the same procedure 11 times: 6 times on California (two models, two agents, a neutral and a "find support" prompt) and 5 times on four datasets whose true effects I knew and the agent did not. I checked the headline number by hand in Excel, ran a multiverse script, read one agent script line by line, and compared the test runs with the answer key.

**What I found.** I separated four levels at which runs could differ. *Numbers*: every number shared by the six California runs was identical (TWFE −27.35, placebo rank 4 of 39, trend-corrected −8.26), and on the test datasets the agent was right every time, including a false effect created by a pre-trend and a staggered design where plain TWFE is biased. *Choices*: runs computed different extra specifications, and did not always declare them. *Interpretation*: verdicts on California ranged from "no clean causal claim" to "the effect disappears". *Actions*: two autonomous runs reinstalled packages without asking, and one also removed a Windows security block.

**Connecting the dots.** Since the numbers never differed, every difference in verdict had to come from a choice. It did: the strongest verdict ("the effect disappears") rests on one specification, a trend correction that subtracts the common decline twice (+0.23 instead of −8.26). Its other estimates are the same as in the neutral runs; this one specification is what separates its verdict from theirs (errors 24, 27). That run had been asked to *support* the hypothesis and moved *against* it; I am not sure why, and with one run it is a signal, not a finding.

**Why it went wrong.** (1) Wrong numbers appeared only while the agent described data in words; once every number came from a script, they stopped. (2) My plan was ambiguous: "a California-specific linear time trend" has two readings, and the agent picked the wrong one. Where the plan was silent, the agent filled the gap and sometimes claimed the plan asked for it (errors 14, 25). (3) The agent uses everything it can see: in the first framing run it read that it was being tested. (4) The goal "finish without stopping" plus permission to act led it to remove obstacles on my computer (errors 23, 29). (5) Each session starts from zero, so the same mistakes came back (errors 15 and 28, 12 and 20), and in unsupervised runs they stayed in the final text.

**What this means for next time.** I would trust the agent to compute, not to conclude. I would write the plan as a specification (exact formula for each check), ask for a table linking each specification to the verdict, check the declared choices and not only the numbers, keep "ask" for shell commands or run `uv sync` after every run, run the analysis more than once and report the range, and test the agent first on data with a known answer, without letting it see the test.
